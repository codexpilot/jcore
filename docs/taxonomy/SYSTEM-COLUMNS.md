# System Columns Reference

**Source of Truth:** JCore taxonomy documentation  
**Purpose:** Define standard system columns used across MetaX tables

---

## Core System Columns (i,d,e,a,fp,s,t,n,g,v)

| Column | Name | Type | Type Flexibility | Description |
|--------|------|------|------------------|-------------|
| i | Identity | INT/BIGINT/UUID | ✓ Flexible | Primary key, record ID |
| d | Date | BIGINT | Fixed | Last edit timestamp (epoch ms UTC) |
| e | Editor | INT/BIGINT/UUID | ✓ Flexible | Last editor user ID |
| a | Active | SMALLINT | Fixed | Binary status (0=inactive, 1=active) |
| fp | Foreign parent | Varies | ✓ Flexible | Optional recursive parent identifier; existence is not guaranteed |
| s | Status | INT | Fixed | Workflow state (generated tables only) |
| t | Type | INT | Fixed | Type reference (legacy, replaced by group-specific patterns) |
| n | Name | TEXT | Fixed | Display name or description |
| g | Group | INT | Fixed | Type group ID (TypeX catalog) |
| v | Version | INT | Fixed | Edit count for optimistic concurrency |

---

## Type Flexibility

Two columns support multiple data types depending on ID generation strategy:

### i (Identity)
- **INT:** Auto-increment sequences (default for MetaX)
- **BIGINT:** Epoch-based distributed IDs
- **UUID:** Universally unique identifiers

### e (Editor)
- **INT:** Simple user ID sequences
- **BIGINT:** Distributed user IDs
- **UUID:** Federated identity systems

**Rule:** Within a single system, `i` and `e` should use compatible types. If `i` is UUID, `e` should typically be UUID or allow NULL.

---

## Additional Common Columns

Beyond the core ten, these columns appear frequently:

| Column | Name | Type | Description |
|--------|------|------|-------------|
| c | Code | TEXT | Immutable identifier (human-readable key) |
| p | Parent | Same as i | Self-referential parent ID |
| ps | Parents | Array of i type | Self-referential parent array |
| di | Domain | INT | Foreign key to DomainX.i |
| o | Ordinal | INT/BIGINT | Sort order or sequence number |

## Usage Contexts

### MetaX Tables (Metadata)
Use a subset of system columns:
```sql
CREATE TABLE mx.domainx (
    i INT PRIMARY KEY,
    d BIGINT NOT NULL,
    e INT NOT NULL,
    a SMALLINT NOT NULL DEFAULT 1,
    n TEXT NOT NULL,
    c TEXT NOT NULL UNIQUE,
    p INT NOT NULL
);
```

**Standard columns:** i, d, e, a, n, c  
**Optional:** p (for hierarchy), di (for domain scoping)

### Generated Runtime Tables (JDB)
Use the seven fixed columns plus optional business columns:
```sql
-- Generated by TableX/ColumnX metadata
CREATE TABLE [schema].[tablename] (
    i BIGINT PRIMARY KEY,
    d BIGINT NOT NULL,
    e INT NOT NULL,
    a SMALLINT NOT NULL DEFAULT 1,
    n TEXT NOT NULL,
    s INT NOT NULL DEFAULT 0,
    v INT NOT NULL DEFAULT 1,
    -- Optional standard columns
    c TEXT,
    fp INT,
    p BIGINT,
    o INT,
    -- Custom business columns from ColumnX
    custom_column1 TEXT,
    custom_column2 INT
);
```

**Fixed seven:** i, d, e, a, n, s, v  
**Optional standard:** c, fp, p, o
**Custom:** Defined via ColumnX metadata

## Column Semantics

### i (Identity)
- Primary key for the table
- Never NULL, unique
- Type varies by ID generation algorithm

### d (Date Last Edit)
- Epoch milliseconds UTC
- Auto-updated by set functions
- Format: `(EXTRACT(EPOCH FROM NOW() AT TIME ZONE 'UTC') * 1000)::bigint`

### e (Editor)
- Foreign key to user/identity table
- Tracks who last modified the record
- Auto-updated by set functions from session context

### a (Active Status)
- Binary flag: 0 = inactive, 1 = active
- Used for soft deletes (set to 0 instead of DELETE)
- NOT used for locking or workflow states

**Important:** `a` is binary only. It does NOT contain:
- Lock bits
- Workflow states (use `s` column instead)
- Multi-value statuses

### fp (Foreign Parent)
- Optional recursive parent identifier.
- Indicates a parent relationship within the same entity type.
- A nonzero value does not guarantee that the referenced key exists.
- Referential integrity is not implied or enforced by the MetaX model.

### s (Status)
- Workflow state for generated business tables
- Values: 0=draft, 1=pending, 2=approved, etc.
- Only in generated tables, NOT in MetaX tables
- Business logic defines state transitions

### t (Type)
- Legacy column for type references
- **Deprecated:** Use group-specific patterns (dtx, ttx, ctx, etc.) instead
- May still appear in older schemas

### n (Name)
- Display name or description
- TEXT type, human-readable
- Required in most MetaX tables

### g (Group)
- TypeX group classifier
- Values: 3=data types, 4=table types, 5=column types, etc.
- Only in TypeX catalog table

### v (Version)
- Edit count for optimistic locking
- Incremented on each UPDATE
- Used to detect concurrent modifications
- Only in generated tables with concurrency control

## Additional Column Details

### c (Code)
- Immutable business identifier
- URL-safe, human-readable
- Often has unique constraint
- Used in APIs instead of numeric IDs

**Example:**
```sql
-- User-friendly references
"user-profile-form"
"invoice-approval-workflow"
"customer-master-table"
```

### p (Parent)
- Self-referential ONLY
- References same table's `i` column
- Root records: p = i (self-reference)
- Used for hierarchical structures

**See:** PARENT-RULES.md for detailed constraints

### ps (Parents)
- Array of parent IDs
- Self-referential ONLY
- All elements reference same table's `i` column
- Used for multi-parent hierarchies

### di (Domain ID)
- Foreign key to mx.domainx.i
- Partitions metadata by solution/template
- Present in most MetaX tables for domain isolation

### o (Ordinal)
- Sort order or display sequence
- Type can be INT or BIGINT
- Used for user-defined ordering
- May allow duplicates or require uniqueness

## Naming Patterns

### Database Level
Use single-letter column names:
```sql
i, d, e, a, n, s, v, c, p, di, o
```

### Variable Level
Use `v_` prefix with column name:
```sql
DECLARE v_i INT;
DECLARE v_d BIGINT;
DECLARE v_e INT;
DECLARE v_a SMALLINT;
```

### API Level
Use descriptive names:
```json
{
  "id": 42,
  "dateLastEdit": 1705334400000,
  "editorId": 100,
  "active": 1,
  "name": "Example Record",
  "status": 2,
  "version": 5
}
```

---

## Validation Rules

### Required vs Optional

**Always required in MetaX:**
- i (primary key)
- d (timestamp)
- e (editor)
- n (name)

**Context-dependent:**
- a (default 1 if omitted)
- c (required if table uses codes)
- p (required if table is hierarchical)

**Generated table specific:**
- s (status, default 0)
- v (version, default 1)

## Examples

### MetaX Table Creation
```sql
CREATE TABLE mx.modelx (
    i INT PRIMARY KEY,
    d BIGINT NOT NULL,
    e INT NOT NULL,
    a SMALLINT NOT NULL DEFAULT 1,
    n TEXT NOT NULL,
    c TEXT NOT NULL UNIQUE,
    di INT NOT NULL,
    mt INT,  -- Model type (group-specific pattern)
    FOREIGN KEY (di) REFERENCES mx.domainx(i),
    FOREIGN KEY (mt) REFERENCES mx.typex(i)
);
```

### Generated Runtime Table
```sql
CREATE TABLE app.customers (
    i BIGINT PRIMARY KEY,
    d BIGINT NOT NULL,
    e INT NOT NULL,
    a SMALLINT NOT NULL DEFAULT 1,
    n TEXT NOT NULL,
    s INT NOT NULL DEFAULT 0,
    v INT NOT NULL DEFAULT 1,
    c TEXT UNIQUE,  -- Customer code
    email TEXT,
    phone TEXT
);
```

### CRUD Function Pattern
```sql
CREATE FUNCTION setmodelx(input jsonb) RETURNS jsonb AS $$
DECLARE
    v_i INT;
    v_d BIGINT;
    v_e INT;
    v_a SMALLINT;
    v_n TEXT;
    v_c TEXT;
BEGIN
    v_i := COALESCE((input->>'i')::int, 0);
    v_d := COALESCE((input->>'d')::bigint, 
        (EXTRACT(EPOCH FROM NOW() AT TIME ZONE 'UTC') * 1000)::bigint);
    v_e := (input->>'e')::int;
    v_a := COALESCE((input->>'a')::smallint, 1);
    v_n := input->>'n';
    v_c := input->>'c';
    
    -- INSERT or UPDATE logic
    -- ...
END;
$$ LANGUAGE plpgsql;
```

## Summary

- **Core system columns** provide consistent structure across all tables
- **Type flexibility** (i, e) supports different ID generation strategies
- **MetaX tables** use subset: i, d, e, a, n, c
- **Generated tables** add: s, v for business workflow and concurrency
- **Binary active flag** (a) is for soft deletes only, not workflow states
- **Single-letter names** at database level for consistency and brevity
